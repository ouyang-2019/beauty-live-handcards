# 已有手卡的改版与交付闭环

用于“这批都完善一下”“资料更新了”“检查是否全部改好”。通用事实规则见data-contract.md，原料写法见single-card-playbook.md，字形修复见qa-protocol.md。本文件负责让新要求落实到最终图片和交付包。

## 先判定问题，再决定重做范围

|反馈/新资料|实际动作|验收证据|
|---|---|---|
|卖点泛、每款像同一篇话术|重新选择该款1—2个明星原料，建立场景→功效方向→原料作用→可感知体验；配角解释协同|成稿能说明这款与其他款有何不同|
|免责声明多、影响推广|按promotion-copy.md改成正向正文，指标、试验类型与条件成组简注；审查意见留制作资料|卖点清楚，单页仍能准确理解数字性质，无重复否定模块|
|新增备案/配方与旧稿不一致|核产品对应关系，撤掉被推翻的旧主轴，再写新稿；不能只往旧图补几个数字|每项核心原料对应配方文件、单元格或备案成分|
|新报告或缺报告页|先匹配同款样品；独立报告页嵌入真PDF，同时回填手卡关键数据|图中指标、条件、报告原件、PDF页码可追溯|
|包装字、瓶型、盒数或遮挡问题|定点修复，不顺带改变已通过事实与画面|修复局部和全页都实看|
|要求核查整批|全批逐款登记，不只复查用户指出的几张|每个产品有最终文件、人工复核结论和哈希|

范围以最新对话为准：表内/表外产品、单页/整套、报告追加、组套另建清单，不以旧任务里的“只做表内”覆盖用户后来的扩大范围。未要求修改的原始资料与旧成图保留；归档用独立目录和索引，不混进正式交付。

## 四份信息分开存

1. **事实表**：准确产品身份、原料/含量、价格规格、报告条件与未核项。
2. **上图成稿**：可以直接给顾客看、主播念的文字；必要限定也属于成稿。
3. **生成/修复提示词**：参考图角色、修改区域、逐字内容、冻结项。
4. **复核记录**：实际观察、失败候选、最终版本、来源与结论。

“记忆点、科技感、护理叙事、直播可讲、这里放水滴、未见资料所以只讲”等是制作语言，不作为消费者卖点。提示词分隔“上图正文”“上图数据标注”和“不上图的执行约束”，生成后仍检查审查意见是否误印上图。按[推广表达与证据标注](promotion-copy.md)精炼文案，同时保留必要的试验类型、条件与示意性质。用户仅要求优化skill时更新规则和范例，不自动启动整批重绘。

## 批量续作与状态

每款记录 `revision_type`：资料改版、质检修复、复核后保留；“保留”必须查看当前图，不能因文件存在默认通过。状态至少区分已生成、待修、已复核、已交付。文件生成数、复核通过数和最终交付数分别汇报。

在允许并行的环境中，按产品编号/图片文件限定执行者所有权；主负责人负责整批集成。审阅者只读。单页完成即可回传路径，便于边做边复核；不要由多个执行者同时打包同一批。代理的“完成”和QA字段都是待复核信息，主负责人应查看最终修改图及关键局部后再批准，不能只转述自评。

一张修完后只重查其相关事实与整页变化；已通过且哈希未变的其他页不反复重绘。遇到可修复问题继续独立工作，缺价只影响价格字段，报告不匹配只限制该报告用途。

## 最终版本的三个证明

- **画面与事实通过**：人工实看最终整页和关键局部，核对标准字形及来源。自动OCR仅辅助，记录脚本不替代看图。
- **来源可追溯**：生成图保存工具返回的真实源路径、实际像素和SHA256；若另存备份，分别记录 `native_source` 与 `archive_copy`，不把输出自身或备份命名当成原生来源证明。报告排版页记录所用PDF及页码，不强求有生成源。
- **交付同步通过**：每款所需模块逐项对齐；最终PNG、PDF内页、索引、ZIP一致，校验ZIP可读且PNG解压后哈希一致。页数从模块清单计算，不硬编码历史27/34/12等数量。

修图后旧批准失效。保留失败记录有助追溯，但正式目录、PDF和ZIP只放当前通过版；旧审查意见要标对应哈希和已解决状态，不能让用户误以为仍未修复。完成报告明确“多少改版、多少修复、多少保留”以及仍影响使用的资料冲突，不把待核项称已确认。
